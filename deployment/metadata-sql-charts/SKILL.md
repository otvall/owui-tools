# SQL → metadata → график

Используй этот скилл при работе с Tool **Metadata SQL Charts**. Подключённый пример
содержит `load_demo_sql_metadata` и `plot_metadata_chart`. Первый метод работает
только с вымышленными данными. Реальная база требует отдельного SQL-адаптера,
сохраняющего результат по контракту ниже; не выдавай демо за реальные данные.

## Последовательность

1. Выясни нужные метрику, период, группировку и единицы из запроса пользователя
   и доступной схемы БД. Не придумывай таблицы или бизнес-правила агрегации.
2. Выполни доступный SQL Tool, который сохраняет результат в `__metadata__`.
   Дождись его ответа: SQL и визуализацию нельзя запускать параллельно.
3. При `status="ready"` возьми точный `dataset_id` и имена колонок из ответа.
   Вызови `plot_metadata_chart(dataset_id=..., x_column=..., y_columns=[...])`.
   Не запрашивай полную выгрузку, не переписывай числа и не передавай rows аргументом.
4. При `code="CHART_READY"` график подготовлен для UI. Не добавляй HTML,
   таблицу или пояснения, если пользователь просил только график. Виджет уже
   сформирован сервером: никогда не генерируй второй график или примерные числа
   вместо скрытых от модели строк. Если нужен текстовый ответ, достаточно «Готово».
   Это серверный результат; не заявляй о проверенном клике или отрисовке браузером.

`__metadata__` и `__user__` передаёт Open WebUI: модель не заполняет их.
Набор существует только в текущем непрерывном серверном запросе. На следующем
сообщении, после перезапуска или возобновления с потерей контекста нужно снова
выполнить SQL. Старый `dataset_id` из истории не гарантирует наличие данных.
Сохранённый HTML графика остаётся в чате независимо от временного набора.

## Формат SQL

Нужна **широкая таблица**: одна строка на X, одна числовая колонка на кривую.
Серверный адаптер преобразует строки драйвера в словари, даты в ISO-строки,
а числа в `int`/`float`. `Decimal` требует осознанного преобразования с учётом
точности; для денег можно использовать целое количество минимальных денежных
единиц и указать соответствующий `unit`. Строки `"125.00"` числами не считаются.

Пример структуры, которую **сервер**, а не модель, кладёт в metadata:

```json
{
  "schema_version": 1,
  "owner_id": "из __user__.id",
  "source": "sales_db",
  "is_demo": false,
  "columns": [
    {"name": "day", "type": "date"},
    {"name": "online", "type": "number", "unit": "RUB"},
    {"name": "stores", "type": "number", "unit": "RUB"}
  ],
  "rows": [
    {"day": "2026-09-01", "online": 120, "stores": 95},
    {"day": "2026-09-02", "online": 145, "stores": null}
  ]
}
```

Место хранения: `__metadata__["metadata_sql_charts_v1"][dataset_id]`.
В примере helper `store_sql_result(rows, columns, metadata, user, source, is_demo)`
записывает этот объект, добавляет владельца и генерирует ID. SQL Tool возвращает
только `status`, `dataset_id`, `row_count`, `columns`, `is_demo`, `scope` и подсказку.
Не возвращай весь `__metadata__` или его namespace как результат инструмента.

Требования к данным:

- X: `date` в формате `YYYY-MM-DD`, конечное `number` или непустая `category`.
  Даты и числа строго возрастают; категории идут в порядке строк SQL.
  X не повторяется и не бывает `null`.
- Y: 1–8 колонок типа `number`, конечные числа либо `null`.
  `null` создаёт разрыв; не подменяй его нулём. Полностью пустая кривая отклоняется.
- Все выбранные Y имеют одинаковый непустой `unit`. Разные единицы — отдельные графики.
- Не более 2000 строк на набор и 4 наборов за запрос в этом примере.
  Для больших выгрузок агрегируй на стороне SQL; не отбрасывай строки молча.
  Это пример передачи в памяти, а не хранилище миллионов строк.

Для длинного результата `day, channel, revenue` сделай pivot/условную агрегацию.
Например, для **демонстрационной** схемы `sales(day, channel, amount)`:

```sql
SELECT day,
  SUM(CASE WHEN channel = 'online' THEN amount END) AS online,
  SUM(CASE WHEN channel = 'stores' THEN amount END) AS stores,
  SUM(CASE WHEN channel = 'partners' THEN amount END) AS partners
FROM sales
GROUP BY day
ORDER BY day ASC;
```

Здесь отсутствие канала даёт `NULL`. Добавляй `ELSE 0` только если по смыслу
отсутствие записи означает нулевые продажи. Для реальной схемы используй её
диалект SQL, согласованные фильтры и параметры. Не суммируй проценты и средние
без корректной формулы. Агрегация по неделе/месяцу должна соответствовать запросу.

## Ошибки

Результат `status="error"` означает, что график не создан. Прочитай `code`,
`message`, `details` и `suggested_action`. Номера строк в `details` начинаются с 1.
Ответы об ошибках не содержат исходных значений ячеек.

| Код | Действие |
|---|---|
| `DATASET_NOT_FOUND` | Выполни SQL в текущем запросе и используй новый ID. |
| `EMPTY_DATASET` | Сообщи, что строк нет; проверь период/фильтры, не выдумывай данные. |
| `COLUMN_NOT_FOUND`, `INVALID_SERIES`, `NON_NUMERIC_COLUMN` | Исправь выбор X/Y по возвращённой схеме. |
| `NON_NUMERIC_VALUE`, `INVALID_NUMBER`, `INVALID_DATE`, `INVALID_X`, `INVALID_CATEGORY` | Исправь SQL или серверное преобразование типов, затем получи новый набор. |
| `DUPLICATE_X`, `UNSORTED_X` | Исправь группировку/pivot или `ORDER BY`. |
| `MIXED_UNITS`, `UNIT_REQUIRED` | Раздели метрики или исправь единицы и преобразование величин. |
| `EMPTY_SERIES` | Исключи пустую кривую, объяснив отсутствие данных, либо исправь SQL. |
| `TOO_MANY_ROWS` | Агрегируй до разумной детализации; не повторяй ту же большую выборку. |
| `METADATA_UNAVAILABLE`, `USER_CONTEXT_MISSING`, `ACCESS_DENIED`, `INVALID_SCHEMA`, `INVALID_METADATA`, `INVALID_ROWS`, `INVALID_ROW`, `MISSING_COLUMN_VALUE` | Нужна проверка серверного адаптера/контекста. Не пытайся обойти проверку доступа. |
| `SQL_EXECUTION_FAILED`, `INTERNAL_RENDER_ERROR`, `DATASET_LIMIT` | Сообщи об ограничении или внутренней ошибке; не утверждай, что данные обязательно неверны. |

Исправляй только то, что следует из ошибки и схемы. Не более двух обоснованных
повторных попыток; затем сообщи конкретную причину и нужное действие.
Не исправляй ошибочные ячейки выдуманными числами.

## Проверка на демо

Обычный пример: `load_demo_sql_metadata(scenario="valid")`, затем
`plot_metadata_chart(dataset_id=<полученный ID>, x_column="day",
y_columns=["online","stores","partners"])`.

Только при явном тестировании ошибок можно использовать `invalid_numeric`,
`empty` или `duplicate_x`. Для `invalid_numeric` ожидается `NON_NUMERIC_VALUE`
для `stores`, строка 3. В тесте восстановления заново загрузи `valid` и построй
график по новому ID. Это смена тестовой выборки, а не исправление реальных данных.
